- (constraint) MVP targets Windows desktop first; mobile in later epics (user decision 2026-10-08)
- (constraint) From ReadMe: no cloud/account dependency, no torrent jargon in UI, sandboxed content, private by default (share only with chosen people), open source
- (direction) User chose Fast path; deliverable is the build contract only (no extra renderings).
- (decision) Stack = C# core + React UI. Why: user and likely contributors know C# and React; rejected Tauri/Rust+librqbit (unfamiliar language), Qt/C++/libtorrent (hard, memory-unsafe), Electron/WebTorrent (heavy, weak mobile). Binds all; prevents a stack nobody on the project can maintain.
- (decision) Shell = .NET MAUI HybridWebView hosting the React build. Why: one C# core and one React UI reach Windows now and Android later; Photino/WPF+WebView2 are desktop-only. [ASSUMPTION] MAUI-on-Windows is good enough for MVP; fallback is a WPF+WebView2 shell, cheap because shell is an adapter.
- (decision) Engine = MonoTorrent (MIT, pure C#, DHT/PEX/LSD/UPnP/magnets/torrent creation). Risks: slow release cadence (3.0.2 stable Aug 2024; 3.9.0-alpha exists), no uTP found in README -> weaker NAT traversal. Mitigation: engine behind a port so it can be swapped (e.g. libtorrent binding). Binds engine; prevents lock-in.
- (decision) Paradigm = hexagonal (ports and adapters). Core has no dependency on MAUI, MonoTorrent, SQLite or the web view.
- (decision) UI<->core only via one typed bridge: commands through HybridWebView InvokeDotNet into a single BridgeHost; events core->UI through one envelope over raw messages. No local HTTP server. Prevents each story inventing its own channel.
- (decision) Core owns all state; UI is a projection (snapshot + change events), mutations only via commands. Prevents two sources of truth.
- (decision) Share identity = app-generated GUID; infohash never leaves the engine adapter. Prevents engine concepts leaking into storage/UI and blocking an engine swap.
- (decision) Sharing references the file in place (no copy/move); removing a share never deletes or alters the original. Received files only under one Received root. Prevents stories disagreeing on what Remove means -> data loss.
- (decision) File selection only via native picker behind IFilePicker in the shell; UI never supplies filesystem paths. Why: web view JS cannot get real paths and it keeps path handling in one trusted place.
- (decision) Vocabulary rule: torrent jargon confined to engine adapter; domain terms Share/Transfer/Person/Invite everywhere else incl. contracts and UI.
- (decision) Network policy centralized in SharingPolicy applied only by the engine adapter. Until the privacy model is decided, public discovery (DHT, PEX, trackers) stays off; local-network discovery only. Why: DHT crawlers harvest infohashes and can fetch content, contradicting 'private by default'.
- (decision) No ComParta-operated or third-party hosted service, no telemetry, no accounts. Device identity = locally generated keypair when needed.
- (decision) Errors cross the bridge as stable codes; UI owns all user-facing text via an i18n catalog (en first, pt-BR planned). Core returns no prose.
- (decision) UI must run in a plain browser against a fake bridge; core must be testable with a fake engine. Why: lets UI and core stories be built and verified independently.
- (decision) Persistence = one SQLite database in the per-user app data folder, touched only by the storage adapter; engine cache/resume data in a sibling folder owned by the engine adapter. [ASSUMPTION] SQLite over JSON because people, invites and transfer history arrive in later epics.
- (version) .NET 10 LTS (10.0.x servicing; 10.0.7 Apr 2026 confirmed, later patches likely); .NET MAUI 10 HybridWebView documented for net-maui-10.0 (learn.microsoft.com, updated Jul 2026); MonoTorrent 3.0.2 latest stable on NuGet; React 19.2.x; Vite 8.1.x. Exact patch numbers not confirmed - pin at scaffold time.

Candidates: DHT with secret link + content encryption; invite carrying direct addresses; optional self-hosted relay. Blocks the 'send to a person' epic, not the MVP.

- (question) OQ-3 Open source license (MIT / Apache-2.0 / AGPL-3.0). MonoTorrent's MIT is compatible with all three.
- (question) OQ-4 Distribution and updates: MSIX vs installer, code signing, update check (an update check is a network call to a hosted service - conflicts with AD on no hosted services unless it is GitHub Releases and opt-in).

- (decision) RECONCILED 2026-10-12 (spine was revised 2026-10-08 without a memlog entry; this supersedes the earlier 'public discovery stays off; local-network discovery only' line). AD-8 now allows three ways to meet, all keyed by the invite: the sender's own address inside the invite, local-network discovery, and DHT. Peer exchange and trackers stay off, server addresses in a pasted invite are dropped, connections are encrypted. Accepted trade-off: the fingerprint is announced on DHT, so a share is unlisted, not secret.
- (decision) 2026-10-12 maintainer accepts that shared files are reachable from the whole internet, not only the local network. AD-8 amended: the invite also carries the sender's PUBLIC address and the app asks the router to open the listening port (UPnP/NAT-PMP, SharingPolicy.AllowPortForwarding already on). The public address comes from the router or the lookup network, never from a third-party 'what is my IP' service (AD-9 holds). The engine reports whether the share is reachable from outside; the UI words it (AD-11). Why: verified 2026-10-12 that GetInviteAsync only adds local interface addresses (x.pe=192.168.x.x), so an invite cannot work from outside the home network; the tracker-less route then depends on DHT alone. Binds engine, core; prevents an invite that works only on the local network, and a public-IP lookup creeping in through a hosted API.
- (decision) 2026-10-12 accepted trade-offs made explicit for family and friends: the invite is a bearer key (anyone holding it can download, no expiry, removing the share is the only revocation); the fingerprint is announced on DHT and crawlers can log it; the sender's public IP is visible to anyone who asks for the fingerprint or connects; RC4 header/full encryption is obfuscation, not confidentiality; uploads are unlimited (no rate or connection cap in src). The stronger per-person-key model stays Deferred, revisit trigger unchanged (before the app is offered outside the maintainer's circle).
- (direction) 2026-10-12 hardening considered and NOT decided (offered to the maintainer, who did not choose it): upload rate limit and connection cap, invites that expire, an option to turn DHT off so only invites carrying an address work. - (decision) 2026-10-13 maintainer asked for the option to name public trackers when sharing. AD-8 amended: trackers stay off unless the person names them in Settings ("public servers", http/https/udp, at most 20). When named, every shared file announces to them (existing shares too, added or removed live) and every invite carries them as tr=, so a plain torrent app can find the sharer from the link alone. The receiver already keeps tr= under AllowServersInDownloadLinks. Trackers help discovery only; they do not make a computer behind a closed port reachable (test 2026-10-13: the sharing port timed out from outside). Binds core (SettingsUseCases, ITransferEngine.SetPublicServersAsync), engine, UI.
