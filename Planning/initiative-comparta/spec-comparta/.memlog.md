- (capability) CAP-1 [MVP] Add a share: a person picks a file on their PC and it joins the list of things they share. Success: after picking a file in the Windows file dialog it shows in the list with name and size; the original file is byte-identical and in the same place.
- (capability) CAP-2 [MVP] See my shares: a person sees everything they currently share. Success: the list shows each share's name and size, shows an empty-state message when there are none, and is the same after closing and reopening the app.
- (capability) CAP-3 [MVP] Remove a share: a person stops sharing a file without losing it. Success: after confirming, the share leaves the list and stays gone after restart; the original file still exists unchanged.
- (capability) CAP-4 [MVP] Plain-language experience: every screen and message is understandable without torrent knowledge. Success: no UI string contains seed, peer, leech, swarm, tracker, magnet, torrent, hash or DHT; every error code has a plain-language message telling the person what to do.
- (capability) CAP-5 [MVP] Missing-file handling: a person learns when a shared file was moved, renamed or deleted outside the app. Success: such a share is marked unavailable in the list and can still be removed. [ASSUMPTION] not in the input; follows from sharing in place (AD-6).
- (capability) CAP-6 [later] Invite a person: a person offers a share to someone they choose, using a channel they already know (email, chat). Success: the sender produces an invite they can paste into an email or chat; only its holder can obtain the share.
- (capability) CAP-7 [later] Receive a share: a person accepts an invite and gets the file. Success: opening an invite downloads the content directly from the sender's device into the Received folder, with no account and no hosted service involved.
- (capability) CAP-8 [later] Follow a transfer: a person sees whether a file is on its way, done or stuck. Success: each transfer shows progress and a plain-language state, and says what to do when it cannot proceed (e.g. the other person's device is off).
- (capability) CAP-9 [later] Safe handling of received content: received files cannot harm the rest of the computer. Success: received content is written only under the Received root, hostile file names cannot escape it, and nothing received is run automatically.
- (capability) CAP-10 [later] Use on a phone: a person does the same things on Android. Success: add, remove, invite and receive work on an Android phone with the same words and flows as desktop.
- (capability) CAP-11 [later] Install and stay current without technical steps. Success: a non-technical person installs on Windows from one download with no extra prerequisites, and updating needs no manual uninstall.
- (capability) CAP-12 [later] Brazilian Portuguese: a person uses the app in pt-BR. Success: every UI string and error message has a pt-BR translation selectable in the app.
- (constraint) No account, no cloud, no hosted service, no telemetry (ReadMe principles 3-4; AD-9).
- (constraint) Target user can use a smartphone and email but nothing more complex; any step needing networking or torrent knowledge is a defect.
- (constraint) Private by default: content reaches only people the sharer chose; public discovery stays off until the privacy model is decided (AD-8).
- (constraint) Sharing never copies, moves, changes or deletes the original file (AD-6).
- (constraint) MVP is Windows desktop only; nothing in it may block the Android shell (AD-1).
- (constraint) Open source; qBittorrent and other clients are reference only, no code copied from them.
- (constraint) Every story must be buildable and checkable on its own (AD-12).
- (decision) Non-goals: public search/discovery of strangers' content; cloud storage or required hosted relays; power-user torrent features (opening .torrent files or magnet links, trackers, speed limits, queues, RSS); in the MVP: sending to or receiving from another person, mobile, installer.
- (decision) Success signal: MVP = a person who has never used a torrent program adds a file and removes it on Windows without help and the original is untouched. Product = two people in different homes move a large family video directly between their devices with no account and no hosted service.
- (assumption) MVP shares single files only; folders (photo albums) come with a later story. ReadMe mentions albums but the stated MVP goal says 'a file'.
- (assumption) In the MVP a share is registered and persisted but reaches nobody outside the local network, because AD-8 keeps the network closed; the MVP proves the UI, bridge, core, storage and engine wiring.
- (assumption) Remove asks for confirmation and states that the original file is kept.
- (assumption) Adding the same file twice is rejected with a plain message rather than creating a duplicate.
- (question) OQ-1 Privacy and discovery model: how do two people behind home routers find each other with no server, and who may download? Blocks CAP-6, CAP-7, CAP-8.
- (question) OQ-2 Windows sandbox mechanism and scanning/marking of received files. Blocks CAP-9.
- (question) OQ-3 Open source license (MIT / Apache-2.0 / AGPL-3.0). Needed before the repository goes public.
- (question) OQ-4 Packaging, code signing and updates; an update check must be reconciled with AD-9. Blocks CAP-11.
- (question) OQ-5 Should sharing a whole folder be in the MVP or the first follow-up?

- (decision) 2026-10-12 (maintainer, architecture AD-8 amended): shared files are reachable from the whole internet. CAP-6 success: the invite works from outside the sender's home network, and the sender is told in plain words whether the share can be reached from outside and what to do when it cannot; someone without the invite still cannot ask for the share (limits in AD-8). Why: verified in code that the invite only carried local addresses, so it could not work between two homes. CAP numbering unchanged; no new capability.
- (decision) 2026-10-12 CAP-7 success: the content comes directly from the sender's device whether in another home or on the same network; no account, no hosted service, never overwrites. CAP-8 text unchanged: 'what to do when it cannot proceed' already covers an unreachable sender.
- (constraint) 2026-10-12 supersedes the earlier 'private by default' line: it holds for people who do not hold the invite; the invite itself is the secret (bearer key, no expiry), so the app never presents it as safe to post publicly (AD-8). 'No hosted service' extended: the sender's public address comes from the router, never from a third-party service (AD-9).
- (assumption) 2026-10-12 replaces 'at least one computer can accept incoming connections': the sender's router either opens the port automatically or the person opens it by hand; a router with no inbound path (carrier-grade NAT) is not solved in this release. Tension noted: a manual router step conflicts with 'no step needing networking knowledge', so what the app tells such a person is an open question.
- (question) 2026-10-12 OQ-1 narrowed. Settled for the first release (AD-8): public address in the invite, automatic port mapping, reachability status. Still open: a stronger model where only chosen people can download; hardening (upload limits, invites that expire, option to turn the public lookup network off); connection through routers with no inbound path; and what the app tells a person whose router will not open the port by itself.
